# Token 预算与阅读策略（非平台计费承诺）

## 先说明
Token消耗取决于所选模型、上下文窗口、自动摘要、重复读文件、代码长度、工具日志、测试次数和失败重试，不能根据 ZIP 文件大小直接计算。中文与代码分词方式不同。

## 本项目开发量级估算
P0 15万–40万；P1 35万–100万；P2 35万–90万；P3 50万–160万；P4 45万–120万；P5 40万–150万 Token（均指所有请求输入、输出与可能缓存重读合计，非精确仪表数据）。阶段合计约220万–660万；预留返工，整体约300万–1000万更稳妥。极端自动循环可显著超出。

## 强制节省措施
- 启动只读README/AGENTS/SCOPE/PLAN，后续依据PLAN逐阶段加载。
- 不让代理每次全量复述PRD或重复分析旧对话。
- 只实现一个真实高质量工作台，不在同一轮生成三个完全不同引擎。
- 每阶段只读变动的源文件与必要测试，不全量遍历node_modules、.next、dist等。
- 限制工具输出：大日志仅保留错误摘要及测试统计，完整日志写本地文件。
- 做完一个阶段停止，用户确认下个阶段；发现前提不成立时先报告阻塞。
- 分开计算 Codex 开发Token和LIMEN运行时LLM API Token。

## 上限管理建议
每阶段使用Codex自身的用量面板看真实数据。如P0显著超过40万Token仍没有连通或RLS测试，先停止调查；若P3超过160万Token仍是静态页面，缩减方案而非无上限迭代。
