# P0 技术验证实施方案

目标：建立能启动的应用及可复现的真实联调入口；在 O*NET 与 Supabase 真实验收前不进入 P1。

## 架构与边界

- Next.js App Router / TypeScript strict / Tailwind；主页公开展示开发阶段状态，`/setup` 提供封闭开发验证入口。
- O*NET 请求固定官方主机、只在服务端读取 key；原始题目、分页、API/数据库版本与答案关联。超时和错误保留可判定状态，不回传上游正文或秘密。
- Supabase 凭据只在服务端使用；会话存入 HttpOnly cookie，资料按 `auth.uid()` RLS 隔离。匿名账户可以删除本人的 Auth 身份及级联资料。
- SQL 以新增 migration 提供，由项目所有者在自己的开发 Supabase 执行；不自动操作未知数据库或生产实例。
- P0 验收脚本创建两个临时匿名身份，以明确标记的合成昵称验证自己读写、跨身份读/写/删拒绝、匿名公众拒绝、刷新与完整删除。只记录状态、结构、数量；不写 JWT、key、真实档案。
- 缺少凭据返回 `BLOCKED` 并以非零退出；本地 mock 单测与 live 验收分开记录。30 位答案真实计分失败必须保留失败，禁止填充成 60 位后声称成功。

## 顺序与出口

1. 建立启动、lint、build、测试配置与 Git 忽略规则。
2. 编写 O*NET 客户端及契约验证，使用明确 mock 的单测覆盖分页/错误/答案顺序。
3. 编写 Supabase 会话、最小昵称资料 API、删除路径与 RLS migration。
4. 执行本地检查、真实 P0 脚本与页面/API 冒烟，记录每项结果。
5. 只有真实 O*NET 30 题/计分/职业结果与双身份 RLS 都通过才能验收 P0 并提交阶段通过的 commit；否则保留带 BLOCKED 标记的恢复点。
