# E1 体验模板与数据库对接约定

用户本轮要求先建模板，再逐步扩充。本阶段不新增表、不执行远端迁移；沿用 Supabase PostgreSQL 的 `experiences.payload`（JSONB）、匿名 Auth 和现有 RLS。

## 医学分类与扩展

首批按临床医学研究生招生常用名称组织：**内科学、外科学、妇产科学、儿科学**。这是四个体验入口，不宣称穷尽临床医学专业。医院岗位分别用内科/外科/妇产科/儿科带教医师，医院科室目录保持独立。

[上海交通大学研招公开目录（2026）](https://yzb.sjtu.edu.cn/storage/gs/web/yzbcn/article/2026/03/696a59c2f7ccecc45649e9d5500ef7a0.xlsx)用于核对上述名称。学术学位与专业学位、招生专业代码、具体方向、培养单位和报考条件必须按目标院校当年目录核验，不能由体验入口推导。当前没有把某院校代码写成全国统一代码。

扩充顺序：学科入口 → 具体亚专业/工作场景 → 案例变体。例如内科学下可逐步补充心血管、呼吸等教学场景，但不将其当作与内科学平级的统一招生分类。新增场景须保持稳定 template_id、版本、三阶段操作、计算规则、成果和来源；模板变化须显式升版。现阶段用单一 e1-1 版本绑定固定合成数据与计算，不支持跨版本历史迁移。

## 当前保存契约

| 字段 | 当前约定 |
|---|---|
| version / simulation | `3.0` / `true` |
| scenario_id | `direction_workbench` |
| template_id / template_version | 白名单模板 ID / `e1-1` |
| source | `curated_template`，不是模型实时生成 |
| direction_id / role | 必须与模板对应 |
| mode | `project` 或 `interview` |
| choices | 恰好三个合法字符串值；保存时不能为 null |
| outputs | 恰好三段操作解释，各 10–3000 字 |
| reflection | 继续/不喜欢的操作、再投入意愿（自述）、后续问题 |
| completed_at | ISO 日期时间；不是数据库提交成功凭证 |
| transcript | 默认空；仅用户选择保存时附带，最多 60 条 |

`GET /api/experience` 读本人所选的一份成果；`PUT /api/experience` 校验后按本人 ID upsert。当前保存会覆盖上一份所选成果，界面有提示。客户端不提交权威结果；服务端 `evaluationCard()` 按模板及 choices 重算 `results`，拒绝额外 metrics 和伪造 source。

JSON/Markdown 导出是成果卡，包含派生结果与 save_status；它不是直接回传 PUT 的原始 payload。未私有保存的成果不会导出为已保存。V2 产品经理及旧 ECG 成果继续读取；旧 V2 本机草稿保留单独导出入口。

## 后续数据库工作边界

多次体验历史、不可变案例快照、动态生成来源、修订号、幂等和本人删除留到 E2，与用户后续整理的数据库结构对接。不得直接以现有单行 upsert 代替历史表，也不得将未验收的迁移记为可用。

数字人仍由用户点击连接，发送角色和当前模板任务；个人画像、操作与回答不自动发送。本阶段没有新 LLM 调用、新供应商或新密钥。按成果动态调整数字人属于 E3，需独立的共享范围预览和提交同步。R2 当前使用三阶段名称和程序结果作体验证据，不接收 transcript，也不推断执业/报考资格。
