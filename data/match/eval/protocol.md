# LIMEN Match · 成对比较标注协议（v1，2026-10-23）

> 适用范围：`data/match/eval/pairs.json` 这一份离线评测标注集，以及 `scripts/match-eval.ts` 生成的
> `docs/testing/match-eval.latest.md` 中所有一致性指标。
>
> **一句话结论（请先读完这一段再引用任何数字）**：本标注集由 **LIMEN 编辑标注（规则化、两轮独立）** 产生，
> **不是独立人类专家标注，也不是"专家共识"**。它可以用来暴露算法与口径的问题，但**不能**用来宣称
> "排序已被验证""匹配准确"。真实专家复核目前**尚未进行**，是已知的、未解决的缺口。

---

## 1. 标注者身份与可信度边界（必须先说清楚）

| 问题 | 事实 |
|---|---|
| 标注者是谁？ | 没有真实独立人类专家参与。本集由两套**显式、可复现的编辑 rubric**生成：第一轮 R1「缺口优先」、第二轮 R2「兴趣高码优先」。两轮都由 LIMEN 编辑（本轮为 AI 执行的规则化流程）产出。 |
| 能不能叫"专家标注"？ | **不能。** 任何文档、页面、对外材料都不得写"专家标注""专家共识""专家已复核"。 |
| 那 α 是什么？ | α 衡量的是**两套编辑 rubric 之间**的一致程度（口径分歧），**不是**人类评分者间信度（inter-rater reliability）。 |
| 为什么两轮用不同 rubric，而不是同一 rubric 跑两遍？ | 同一 rubric 是确定性脚本，重复执行必然得到完全相同的标签（本报告里"确定性复跑差异 0 行"就是证据），α 会等于 1 但**没有任何信息量**。用两套有依据的编辑优先级，才能测出"标注口径本身是否稳定"。这比"重复同一规则"更严格，但仍然是**替代品**，不能冒充人类信度。 |
| 与引擎的关系？ | 标注 rubric 使用与引擎**不同**的量（Iachan 高码重合、缺口计数、欧氏距离；引擎用 Pearson 轮廓相关加权几何合成），且**不读取引擎输出**。因此 τ 不是循环论证；但两者共享同一批画像/岗位事实，存在"同源"的残余风险，这一点在局限里列明。 |
| 可信度边界 | 本集可以支持：性质检验（单调性、尺度不变、真值恢复）、口径敏感性、稳定性。**不能**支持：准确率、预测效度、亚组公平性、录取概率、任何"适合度"宣称。兴趣量表对职业选择的历史命中率约五成（Hanna & Rounds 2020），这本身就封死了"高匹配=适合"的叙事。 |

## 2. 标注单位

- **单位 = 一个岗位对（pair）**：同一固定画像 × 两个岗位（A、B），无序排列，按夹具顺序 `a` 在前、`b` 在后。
- 唯一键 `pair_id = "{profile_id}::{a}::{b}"`；两轮共用同一 `pair_id`，用 `pass` 字段区分。
- 每对**一行/轮**，因此唯一对数 × 2 = 标注行数。当前集：12 画像 × C(8,2)=28 对 = **336 唯一对**，
  两轮共 **672 行**（脚本 `--annotate` 输出并在报告中复核）。

## 3. 标注问题（措辞固定，不许改写）

> **在给定画像下，A 与 B 哪个岗位更值得优先探索？**
>
> 判据只允许来自画像与岗位事实（兴趣六维、技能要求与自评等级、专业/资格门槛）。
> 不判断"能否录取""能否成功""是否适合"；不引入外部薪资/地域/院校信息。

**为什么这样问**：LIMEN 对外只给"名次区间 + 四档"，不给综合适合度百分比。标注问题必须与产品宣称同构，
否则测出来的"一致性"没有产品含义。

## 4. 量表（4 类，名义尺度）

| 标签 | 含义 | 允许条件 |
|---|---|---|
| `A` | A 明显更值得优先探索 | 判据差 ≥ 阈值（见 §6 各 rubric） |
| `B` | B 明显更值得优先探索 | 同上，方向相反 |
| `tie` | 两者在本 rubric 下**看不出**差别（差 < 阈值） | 必须能写出差额，不允许"感觉差不多" |
| `undecidable` | **无法判断**：关键事实缺失/兴趣平坦/资格全未知，任何方向都会是编造 | 例：六维兴趣缺失、剖面 sd 过低、两个岗位硬资格都不满足 |

- `undecidable` **是合法结论**，不是失败。它必须保留在数据里，不能为了"凑对数"改判成 A/B/tie。
- 反过来，也不允许把"差 < 阈值"写成 `undecidable` 来逃避判断：差 < 阈值 → `tie`。

## 5. 数据来源（与标注集严格绑定）

| 文件 | 内容 | 性质 |
|---|---|---|
| `data/match/eval/profiles.json` | 12 个固定画像（真实模式 4 + 边界模式 8） | **合成画像**，不是真实用户 |
| `data/match/eval/occupations.simulation.json` | 8 个岗位夹具（兴趣六维 + 3 项技能要求 + 部分硬资格） | **合成夹具，不是岗位标准**，不得用于产品展示 |
| `data/match/eval/synthetic-ground-truth.json` | 已知 RIASEC 真值 + 噪声水平 + 种子 | 仅供真值恢复实验 |

**边界模式覆盖**（每个都必须在报告里单列一致率）：
兴趣平坦（`p05`）、技能缺失/覆盖不足（`p06`）、资格未知（`p07`）、
跨考（`p08`、`p09`，专业不满足医学门槛）、非跨考（`p10`，门槛满足）、技能满级（`p11`）、技能全部未接触（`p12`）。

> 说明：`occupations.simulation.json` 里的兴趣向量与技能要求是**为了"有可比对象"而合成的评测夹具**。
> T1 的 `data/match/occupations.official.json`（O*NET 官方标准）落地后，必须用官方标准 + 真实/自评画像重跑；
> 契约禁止"合成画像 × 官方标准"混算，所以这一步不能由本脚本自动完成（见 §10）。

## 6. 两轮独立标注的程序

### 6.1 共同前提（属于"标注问题定义"，两轮共享）

1. **硬资格优先，且不可被其他维度抵消**：任一岗位硬资格明确 `not_met` → 另一个胜出；
   两者都 `not_met` → `undecidable`。资格 `unknown` 不参与该判断（不静默假设满足，也不静默否决）。
2. 只使用画像与岗位事实，**不读引擎输出**（`match()` 的分数、名次、`rank_range` 一律不进入 rubric）。
3. 阈值提前写死，不因样例调整（调阈值必须升 `protocol` 版本并重标全量）。

### 6.2 第一轮 R1 · 缺口优先（`rubric_ref = R1-gap-first`，`rater = limen-editor-r1-rule-based`）

```
1) 硬资格前提（§6.1.1）→ 若可判则直接出标签
2) 计算两个岗位的缺口事实：
   mustGap  = Σ[ must_have 项且 current < required ]        （关键缺口个数）
   severity = Σ[ gap × (must_have ? 2 : 1) ]                 （缺口严重度）
   unknown  = current 未知的项数（不进分母、不当 0）
3) mustGap 少者胜
4) 若相同：severity 差 ≥ 1 → severity 低者胜
5) 否则 → tie
```
**不看兴趣**。理由：一个只掌握技能与资格事实的编辑，会先问"还差多少门硬技能"。

### 6.3 第二轮 R2 · 兴趣高码优先（`rubric_ref = R2-interest-topcode-first`，`rater = limen-editor-r2-rule-based`）

```
1) 硬资格前提（§6.1.1）→ 若可判则直接出标签
2) 画像兴趣缺失 → undecidable
   画像兴趣 sd < 1 → undecidable（平坦剖面不判断轮廓）
3) 取用户 top-2 兴趣维、岗位 top-2 兴趣维，行编辑性简化的 Iachan 重合分：
   同位：第 1 位重 3 分、第 2 位重 2 分；跨位重 2 分（满分 5）
4) 高分胜
5) 若相同：六维欧氏距离差 ≥ 0.25 → 近者胜；否则 tie
```
**不看缺口计数**（只在平局后用距离，不用技能）。理由：一个先问"你想做什么"的编辑，会以兴趣形状为主。

### 6.4 独立性如何保证（代码层，可审计）

- `rubricGapFirst(profile, a, b)` 与 `rubricInterestFirst(profile, a, b)` 的**签名里只有事实**，没有对方的输出；
  `buildPairRows()` 先完整跑完第一轮、再跑第二轮，第二轮**不可能**读到第一轮标签。
- 生成顺序固定（画像按 `profiles.json` 顺序、岗位按 `i<j` 组合），因此**同输入必然同输出**；
  报告会给出"确定性复跑差异行数"与"`pairs.json` 与当前夹具逐行比对差异行数"，两者都应为 0。
- **盲化说明**：第二轮看不到第一轮结论（代码层保证）。本轮没有做"对人盲"这一步，因为本来就没有人类标注者；
  引入真实专家后，盲化必须由流程保证（见 §11）。

## 7. 冲突处理：保留，不抹平

两轮不一致时按以下顺序处理，**任何一步都不许"投票修补"**：

| 情形 | 处理 |
|---|---|
| A/A 或 B/B | 一致，进入主口径聚合 |
| tie/ab 或 A/tie | 记为"tie vs 判定"，**不聚合**（保留在数据里） |
| undecidable 与任何判定 | 记为"含 undecidable"，**不聚合**（保留） |
| A/B 或 B/A | **冲突，原样保留**，标为无标注（不选边） |

聚合规则只用于把"对级标签"变成"画像内顺序"：

1. **主口径**：只采信两轮一致的 A/B；tie/undecidable/冲突 = 无标注。
   用胜负累计（Borda）得到画像内顺序，再用 Kendall τ-b 与引擎顺序比较。
2. **可比性门槛**：画像内决定性对 < 该画像岗位对数的一半时，判为"标注未形成可比排序"，**不给 τ**
   （否则只是按 ID 字典序排出来的假顺序）。
3. **敏感性口径**（因为主口径有选择性偏差，必须并列报告）：
   - 冲突以第一轮 R1 为准；
   - 冲突以第二轮 R2 为准。
   三种口径方向一致才谈得上"稳健"；不一致时，报告必须写明是"引擎与某一口径吻合、与另一口径不吻合"。

> τ 主口径只采信"两轮都同意"的对，天然偏向容易判断的样本，因此**单看 τ=0.98 是误导性的**。
> 报告同时给出三种口径；当前结果是主口径 0.98（112 对）、R1 为准 0.47（174 对）、R2 为准 0.86（234 对）。
> 这说明引擎顺序与"兴趣优先"口径高度吻合、与"缺口优先"口径不吻合 —— 这是取舍问题，不是精度问题。

## 8. 统计与解读边界

| 指标 | 门槛 | 来源 | 达不到时怎么写 |
|---|---|---|---|
| Krippendorff α（名义） | ≥ .80 可信；.67–.80 仅探索 | `docs/MATCH_V2_PLAN.md` §5.1 | 直接写"**未达标**：α < .67，两轮标注一致性不足以支撑排序结论" |
| Kendall τ | ≥ 200 对才可定量解读 | §5.1 | 写"样本不足，仅探索性"；**不报 p 值** |
| 权重扰动翻转率 | ≤ 15% 标 stable | §5.1 | 写实际百分比与超阈值的岗位 |
| Top-k Jaccard | 计划原文无门槛，编辑参考 ≥ 0.8 | 本协议自定 | 标注为"参考门槛（非计划原文）" |
| 单调性 / 尺度不变 / 无关字段不变 | 100% 通过 | §5.1 | 列出失败样本与前后数值 |
| 真值恢复 Spearman | ≥ 0.8 | §5.1 | 按噪声水平逐行给均值与分位数，不报 p 值 |

其他硬性规则：

- **不报 p 值**（§5.1）。样本量不足时不得用显著性话术补救。
- 所有数字必须由 `npx tsx scripts/match-eval.ts` 真实产出，**禁止手填、禁止估算、禁止事后挑选口径**。
- `undecidable`、`tie`、冲突的数量必须在报告里单独披露（缺失即偏差，Rubin 1976）。
- 不允许写"准确率""预测效度""录取概率""适合度"——样本与结果标签都不支持。

## 9. 复现步骤

```bash
# 1) 生成/重生成标注（两会话无关，确定性）
npx tsx scripts/match-eval.ts --annotate   # 写 data/match/eval/pairs.json（336 对 × 2 轮 = 672 行）

# 2) 生成报告（读 pairs.json，跑全部指标）
npx tsx scripts/match-eval.ts              # 写 docs/testing/match-eval.latest.md 与 .json

# 3) 校验统计实现与确定性
npx tsx --test tests/match-eval.test.ts
```

- 随机性只在两处出现，且都由固定种子控制：单调性抽样（`seed+1`）、真值恢复噪声（`seed+7`，见
  `synthetic-ground-truth.json` 的 `rng.seed`）。其余全部确定性。
- 基准时间固定为 `2026-10-23T12:00:00Z`（引擎用它判断体验/招生有效期），因此报告可逐位复现。

## 10. 已知局限（逐条，不许省略）

1. **没有人类专家。** 本集是规则化编辑标注；α 是口径一致性，不是评分者信度。
2. **两轮 rubric 由同一作者设计**，存在"作者偏见"共源风险：两套口径的分歧方向本身也受作者影响。
3. **岗位是合成夹具**，不是真实岗位标准；换成官方 O*NET 标准后，标签必须重标（不能复用）。
4. **画像只有 12 个、岗位只有 8 个**，唯一对 336 个；剔除 tie/undecidable/冲突后，主口径决定性对仅 112 个，
   远低于 §5.1 的 200 对门槛 → τ 只能定性解读。
5. **契约禁止合成画像与官方标准混算**（`matchInputSchema` 的 simulation 一致性校验），因此官方标准落地后，
   端到端排序评测需要**真实/自评画像**，不能由本脚本自动补跑。
6. 兴趣量表对职业选择的命中率约五成；"匹配度高"不意味着"适合"或"会成功"。
7. 标注问题只覆盖"优先探索顺序"，不覆盖"该不该转行""值不值得投入"。

## 11. 真实专家复核的准入条件（未来必须做）

要把它从"编辑标注"升级为"专家标注"，至少要满足：

1. **≥ 2 名独立专家**，专业背景覆盖临床医学 + 数据/统计，且与 LIMEN 有利益隔离；标注前签署
   "不对外引用未发布材料"的说明。
2. **同一份 protocol、同一份 rubric**，双人独立标注，**盲化**（互不可见对方标签，且不接触引擎输出）；
   记录每人的标注耗时与不确定项。
3. **样本量 ≥ 200 对**（§5.1），且覆盖本协议 §5 的每个边界模式；每个模式下不少于 20 对。
4. **先算 α 再算 τ**：α ≥ .80 才允许把 τ 当定量指标；.67–.80 只作探索；< .67 先改 rubric，不许直接发布 τ。
5. 冲突由**第三名裁决人**在 blinding 条件下裁决，裁决理由归档；不允许"多数票"或"作者裁定"。
6. 复核结果单独落盘（例如 `pairs.expert.json`），**不得覆盖**本编辑标注集；报告中两份并列，标明来源。
7. 人工标注的酬劳、招募渠道与筛选标准留档，便于复算与审计。
